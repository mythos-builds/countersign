# Countersign binding — spec v1

*v1, 2026-11-14: implemented in `lib/`, tested in `test/`. v0 was the ideation-week draft of 2026-11-12, kept as it was under the tag `start-2026-11-14`; §12 lists what changed.*

## 1. Purpose
Let anyone check, with no server of ours, that **one person controls both a Bitcoin Cash address and a Nostr key**, so that a Nostr name can be paid in BCH on chain, with no custodian and no Lightning. Neither key ever leaves its wallet; no key is reused across the two systems.

## 2. Terms
- **npub**: a Nostr public key (NIP-19 form). **Address**: a BCH CashAddress, P2PKH only in v1. A token-aware address (`z…`) has the same payload and decodes as the same key hash.
- **Commitment**: a BCH transaction spent from the address that names the npub (the BCH half).
- **Claim**: the person's NIP-39 identity list, kind 10011, carrying the address and the commitment's txid (the Nostr half).
- **Binding**: a claim + a commitment that point at each other and both verify.

## 3. The BCH half: commitment transaction
1. At least one input spends a P2PKH output locked to the claimed address. Its signature's sighash byte is one of `0x41, 0x61, 0xC1, 0xE1` (every variant that covers all outputs); anything else is refused, so a signature cannot be re-used with another data output.
2. Exactly one data output carries the tag: `OP_RETURN <tag: 4 bytes> <sentence>`, exactly two pushes, where *sentence* is the UTF-8 text of NIP-39's own wording: `Verifying that I control the following Nostr public key: npub1…` (about 128 bytes in total, under the 223-byte relay limit). Data outputs without the tag are ignored; two tagged outputs make the transaction invalid as a commitment.
3. **Tag: script bytes `43 53 47 00` (« CSG\0 ») = protocol ID `0x00475343`**, Lokad style (pushed as `0x04` + 4 bytes, little-endian, like SLP's « SLP\0 » = `0x00504c53`). In the allowed range and not in the registry (`bitcoincashorg/bitcoincash.org` `etc/protocols.csv`, read 2026-11-12); claiming it there is a courtesy PR after the event.
4. At most **20 inputs**: a verifier fetches every parent, so a commitment cannot make it fetch hundreds.
5. The builder (`buildCommitment`) spends the address's own coins, puts the data output first and the change back to the same address (at least 546 sat). The fee is 1 sat/byte of the transaction as signed with the largest unlock a wallet may produce (108 bytes: a 73-byte ECDSA signature, a 33-byte key, two push bytes), so it never falls under 1 sat/byte whether the wallet signs with ECDSA or Schnorr. The whole transaction is about 330 bytes.
6. Coins carrying CashTokens are never spent by the builder (see §10).

## 4. The Nostr half: claim event
- Kind **10011** (NIP-39, replaceable), tag `["i", "bitcoincash:<cashaddr>", "<txid>"]`. The identity reads exactly like the address a wallet shows (`bchtest:` on chipnet) and must match `^(bitcoincash|bchtest):[cashaddr charset]+$`; the txid is 64 lowercase hex. Addresses are compared by decoded hash and prefix, never as text.
- The builder (`buildClaim`) **merges** into the person's current kind 10011: it keeps every other tag, drops older `bitcoincash`/`bchtest` identities, and dates the new event `max(now, previous + 1)` so it replaces the old one.
- `["t", "countersign"]` is added by default: it marks bound names for a public directory (no directory page in v1).
- Published to the person's write relays (kind 10002, up to five) and the five defaults. A name created on the bind page also gets a kind 10002 listing the defaults and, if the person typed one, a kind 0 name.

## 5. Verification: `verifyBinding(npub[, address])`
Trusts nothing it is handed.
1. Read the author's relay list (kind 10002: up to five `r` relays not marked `read`), then fetch the newest kind 10011 by the author from those relays, up to three hints (from an nprofile or a NIP-05 document) and the five defaults. Newest `created_at` wins; on a tie, the lowest id (NIP-01). Verify its signature **on a fresh copy parsed from JSON** (nostr-tools caches « verified » on event objects); author and kind must match.
2. Take the `bitcoincash` (or `bchtest`) identities; with an `address` given, only the one that names it. Several → the first, with a warning. Decode; require P2PKH.
3. Fetch the transaction by txid from the Fulcrum servers (all four defaults are connected; each is asked in turn): the bytes must hash to the txid. One honest server suffices; a dishonest one can only fail to answer. That holds for transaction bytes only: heights, block headers and the address history (steps 8–9) carry no hash, so every live server is asked for them. The chain tip is the lower median of their answers (no one server can add confirmations), a header the newest of those offered (no one server can make a binding look old), and the history the one most of them give, put in height order with the mempool last; a split makes the binding `unchecked` (step 9), and a tip or header that can't be settled leaves its age unknown.
4. Require exactly one tagged data output, two pushes, the NIP-39 wording; the npub in it must equal the claim's author.
5. Fetch every parent transaction by id, re-hash each, rebuild the source outputs. Find an input whose source output is locked to the address, whose unlock is `<sig> <pubkey>` with `hash160(pubkey)` = the address payload, and whose sighash byte is allowed (§3.1).
6. Run the BCH virtual machine (libauth, consensus rules: a mined transaction is valid even if non-standard) on the whole transaction with those source outputs. Any failure = invalid.
7. Refuse key reuse: the BCH public key's x-coordinate must differ from the Nostr public key.
8. From the address history: in a block → `verified`, mempool only → `pending` (both halves valid). `confirmations` = tip − height + 1 and `boundSince` = the time in the block header, or both `null` when the servers give no usable tip or header (the age is then unknown).
9. Supersession: the transactions after the commitment in the address history are read, newest first, up to 300; one that passes steps 3–7 for this same address and names another npub makes the binding `superseded`. A transaction merely *sent to* the address cannot pass step 5, but anyone can add such transactions for a few hundred satoshis each, so a binding is `unchecked` when step 9 can't read them all: more than 300 follow the commitment, or the history is unavailable, leaves out the commitment, or lists a transaction (or a later commitment's parent) that no server returns.

Result: `{status, npub, address, txid, confirmations, boundSince, warnings, reason?, supersededBy?}`. `warnings` includes `new` when the commitment is unconfirmed, under 24 h old or of unknown age, and says why when the age is unknown.

## 6. Statuses
`verified` · `pending` (payable, shown as new) · `superseded` (with the newer npub and txid) · `unchecked` (both halves valid, but §5.9 couldn't rule out a newer binding; with a reason; never payable, and a login app treats the key as having no address) · `invalid` (with a reason). A newest claim that names no BCH address means the person unbound: `invalid`, « the newest claim names no BCH address ».

**Rotation** needs no extra rule, only the two « newest wins » above, and the bind page offers it once a name is chosen: a name already bound is shown its address and commitment, and may (a) **move to another wallet** (the usual steps: a new commitment, then a claim naming the new address replaces the old claim), or (b) **unbind** (`buildUnbind`: the current identity list without its BCH address and the wall tag, dated after it). A **new Nostr key** binds the same wallet from that key: the newer commitment in the address history makes the old name `superseded` (§5.9).

## 7. Discovery (no indexer of ours)
- **By name** (`resolveName`): an npub, an nprofile (its relay hints are used), 64-hex, a `nostr:` link or profile URL holding one, or `name@domain` through NIP-05: `https://domain/.well-known/nostr.json?name=…`, no redirects followed, the document must list that exact name; relay hints are `wss://` only, five at most.
- **By address** (`findByAddress`), two independent roads:
  - relays: filter `{"kinds":[10011], "#i":["bitcoincash:q…"]}` (single-letter tag, indexed by relays), keeping claims that name the address exactly;
  - the chain alone: the last 50 transactions of the address history (Fulcrum `blockchain.address.get_history`); each tagged data output names a candidate npub.
  Every candidate goes through §5 with the address fixed. Of the `verified`/`pending` ones, the newest commitment in the address history wins; otherwise an `unchecked` one, otherwise a `superseded` one; `null` when no candidate's binding holds. An `invalid` candidate is never the answer: anyone can name any key in a payment to the address (546 sat) or in a claim, and the page would show that key's name and picture. The result says which roads found it (`via`).

- **The wall** (`listWall`): relay filter `{"kinds":[10011], "#t":["countersign"]}`, newest claim per author. A relay only suggests a name: its newest claim, read from its own relays too, must still carry the tag (a person leaves the wall by publishing a claim without it), then the binding goes through §5. Only `verified` and `pending` names are shown, newest claim first, at most 30, four checks at a time. Anyone can tag junk claims, so candidates are checked newest first until 30 names pass (200 claims at most), and a claim dated more than 10 minutes ahead is ignored.

## 8. Paying a name
1. **WizardConnect rail**: the page builds the payment from the payer's own coins (found from the wallet's public keys), the wallet signs and broadcasts (`broadcast: true`, said in words on the page). The page checks the signed transaction has exactly the outputs it built before sending a copy itself.
2. **Plain rail**: a `bitcoincash:` payment link / QR for any wallet; « paid » detected live through a Fulcrum address subscription.
3. **Receipts** (optional, public; `lib/receipt.mjs`). After a payment the payer may post a **kind 1 note** signed by their Nostr key (`receiptTemplate`): content « Paid nostr:<payee npub> <amount> BCH on chain with Countersign. » and an explorer link (plus the payee's pay link when the page is served over HTTPS); tags `["p", <payee>]` (the payee is notified), `["i", "bitcoincash:tx:<txid>", <explorer URL>]` and `["k", "bitcoincash:tx"]` (NIP-73's blockchain transaction id; NIP-73 names no word for BCH, so the word of its URI scheme and addresses), `["t", "countersign"]`. Sent to the payer's write relays, the payee's read relays (NIP-65) and the five defaults.
   **Listing** (`listReceipts`): filter `{"kinds":[1], "#p":[<payee>], "#t":["countersign"]}` on the payee's read relays and the defaults. A note counts only if: its signature verifies on a fresh copy · it names exactly one BCH transaction · its author is not the payee · the txid is in the payee's address history · the transaction, fetched and re-hashed, carries no input with the payee's own key (the payee's change is no payment) · it pays the payee's bound address. The amount shown is what the chain says it pays, never the note's text.
   **Who paid**: anyone can post a note about anyone's payment, so a note alone proves nothing about the payer. It is `bound` only when its author's own binding verifies (§5) and that bound address signed an input of the payment over every output (§5.5–5.6: parents re-hashed, the allowed sighash bytes, the VM); otherwise it is a `claim`, shown without the author's name or picture (« someone paid », a note by that npub « says it was them, unproven »): `created_at` is the author's word, so the earliest claim is anyone's to take. One row per transaction: a `bound` note wins, otherwise the earliest note; newest payments first (unconfirmed, then by height); at most 20 transactions are checked, and every note naming one of them (the relay query returns 200 notes at most; one binding check per author, one fetch per transaction).
- Paying an npub that has not bound is not possible by design (deriving an address from a Nostr key = the key reuse the bounty forbids).

## 9. Login (challenge-response, another app)
NIP-98 HTTP auth over a single-use challenge (`lib/login.mjs`).
1. **Challenge.** `loginGate({ url })` is the app's side; `url` is its login endpoint as people reach it. `challenge()` → `{ url: <endpoint>?nonce=<32 hex>, method: "POST", expiresAt }`. A challenge lives 120 s. Open challenges are kept in the gate's memory; expired ones are dropped when a new one is issued; at most 10 000 are open, past that the oldest goes.
2. **Answer.** The person's key (NIP-07 extension, remote signer or secret key) signs `{kind: 27235, created_at: now, tags: [["u", <that url>], ["method", "POST"]], content: ""}` (`loginTemplate`), sent to that URL as `Authorization: Nostr <base64 of the JSON event>` (`authorizationHeader`).
3. **Check** (`check(authorization, {url, method})`, `url` = the absolute URL the request reached), in this order: the header's form · a JSON event · its signature, on a fresh copy · kind 27235 · `created_at` within ±60 s of the app's clock · `u` equals the request URL exactly · `method` matches · the URL's origin and path are the endpoint's and its nonce is open. Then the nonce is spent, and an expired one is refused. → `{pubkey, npub}` or `{error}`. A failure before the nonce step leaves the challenge open for the right answer; a replay finds the nonce spent.
4. **Who is this?** The app runs `verifyBinding(npub)`: « signed in as …, pays to … ». No identity provider is asked.
5. **The wallet too (optional).** `walletChallenge({ npub, address })` (npub = who signed in, address = step 4's answer) asks the wallet behind the address for a live signature, with BIP-322's construction on BCH: a made-up parent transaction (version 2; one input spending the null outpoint with `OP_0 <tagged SHA-256 of the text>`, tag `Countersign/wallet-proof`; one output of 0 sat to the address), and a spend of its output 0 whose only output is a Countersign data output, `OP_RETURN "CSG\0" <text>`, text = « Sign in to <host> as <npub>, one-time code <32 hex> ». The person's page finds the address in the wallet's public keys (`findAddressPath`, receive and change, first 2 000 each) and the wallet signs input 0 with `broadcast: false`. The parent can never be mined (a null outpoint outside a valid coinbase), so the signed spend can never be broadcast: it moves nothing and costs no fee. A challenge lives 300 s. `walletCheck(signedHex)` checks, in this order: a transaction · one input · its outpoint names an open challenge (the parent's id) · with the signature taken out, it is byte for byte the transaction asked for, rebuilt from the challenge · the input is signed by the address over every output (§5.5) · the BCH virtual machine accepts it. Then the challenge is spent, and an expired one is refused. → `{npub, address, publicKey}` or `{error}`; a failure before the spend leaves the challenge open.

The answer is a standard NIP-98 event: one made by nostr-tools' `nip98.getToken` is accepted (tested). Shipped: `examples/login-server.mjs` (node:http, `GET /challenge`, `POST /login`), `examples/login-client.mjs` (signs in, then replays: 401), and `app/demo-login/`, a separate app that imports only the library and nostr-tools.

Deployment notes: tie each nonce to the browser session that asked for it (a cookie), so an answer signs in only that session · rate-limit `challenge()` · several processes need a shared challenge store · serve over HTTPS, so the URL in `u` is the one the person meant.

## 10. Security
- Never spend a coin carrying tokens: tokens left out of the outputs are burned. Fulcrum's `exclude_tokens` and `token_data` are the server's word, so each coin is checked against its parent transaction, fetched and re-hashed: it must carry no token there and have the value and lock the server gave, or it is left out.
- The wallet shows the data output as raw hex, so the signing prompt says in words what is signed.
- Relays and Fulcrum servers cannot forge a binding (signature checks, re-hashing, the VM); hiding can make a bound name look unbound. Heights, headers and histories are the servers' word, cross-checked between the servers a reader reaches (§5.3): one dishonest server among honest ones changes no verdict, but a reader who reaches only dishonest servers can be shown a wrong age, or a replaced name as current. Likewise a reader whose relays all hide the newest claim can be shown a name that was unbound or moved. A fuller fix would check merkle proofs against headers chained to a checkpoint.
- A stolen Nostr key can re-point the claim, but not forge a commitment; « bound since » and the `new` warning are the user's defence. A tricked wallet can only attach its own address.
- A commitment cannot make a verifier do unbounded work: at most 20 inputs (§3.4), at most 300 later transactions read (§5.9; more gives `unchecked`), 50 history entries on the chain road (§7).
- Profile data shown from kind 0 is reduced to plain strings; pictures are `https://` only.
- A receipt can point at anyone's payment: only a `bound` proof names the payer, and amounts come from the chain (§8.3).
- Remote signers (NIP-46, `lib/remote.mjs`): the Nostr key stays in the signer app; the page holds a throwaway session key only. It connects by a `nostrconnect://` link (QR) whose secret the signer must send back, or by a pasted `bunker://` link, and asks for `get_public_key` and only the kinds it signs (10011, 1, 27235). Every event a signer returns is re-verified on a fresh copy, must carry the identity's key, and must be exactly the event asked for (kind, `created_at`, tags, content); anything else is refused (tested).

## 12. Changes from v0
- The tag is final: `CSG\0` (§3.3). New limits: 20 inputs (§3.4), 300 later transactions (§5.9). Data outputs without the tag are ignored (§3.2). The fee rule is written down (§3.5).
- Five default relays instead of three; relay hints from nprofile and NIP-05 (§5.1).
- Fulcrum: one hash-checked answer from any server instead of « two servers or more »; the hash makes extra copies unnecessary (§5.3).
- A newer claim with no BCH address gives `invalid` with its reason, not `superseded` (§6).
- Discovery by address is specified as two roads that each lead to the full check (§7).
- Login is implemented: exact rules for the nonce, the window and the order of the checks, plus deployment notes (§9).
- Rotation is offered on the bind page: move to another wallet or unbind (`buildUnbind`), and a new Nostr key supersedes the old name from the same wallet (§6).
- After the review of 2026-11-16: a binding whose later history can't be read in full is `unchecked`, never payable; 30 small payments to the address used to hide a rotation (§5.9, §6). Heights, headers and histories are asked of every live server, where the first server's word used to decide age, confirmations and the history's order (§5.3, §5.8). Coins are checked against their parent transactions before they are spent (§10). Every receipt note naming a payment is checked, where 5 backdated notes used to push a proven one out; claims show no name (§8.3). Discovery by address no longer answers with an `invalid` candidate (§7). The wall keeps looking past junk claims (§7).
